# Ops Change: Provision foundational external accounts (Vercel, Supabase, AI Gateway, MSG91, Bhashini, Sentry)

## What & Why

Closes architecture v1 P1 Issue ("Vercel project (region `bom1`), Supabase project (region `ap-south-1`), AI Gateway provider keys, MSG91 account, Bhashini API keys not yet provisioned"). Stands up the six external services the approved foundational architecture depends on so the scaffolded repo can run end-to-end and the first feature bet can begin work without an account-setup blocker.

No code changes — this is account/dashboard work plus environment-variable wiring. Per workflow rule: all ops are full-discipline regardless of perceived risk. Security Reviewer (Codex) auto-engages because the change touches secrets, IAM, and auth.

## Affected systems

- **Vercel** — hosts `apps/web` (Next.js 16, region `bom1`).
- **Supabase** — Postgres 16 + pgvector + Storage in `ap-south-1` (entire data layer per § Foundational Data Model).
- **Vercel AI Gateway** — routes LLM calls to Anthropic + OpenAI (`packages/ai/src/gateway.ts`).
- **MSG91** — SMS OTP fallback for the ~5–15% passkey-incapable cohort (`packages/auth/src/otp.ts`).
- **Bhashini / AI4Bharat** — vernacular ASR/TTS for Hindi at launch (`packages/ai/src/speech.ts`).
- **Sentry** — error + RUM telemetry (web + mobile projects).
- **Local dev environments** — `.env.local` populated via `vercel env pull`; EAS Secrets via `eas secret:push`.
- **Repo** — `.env.example` is the source of truth for the var keys; values never committed.

## Blast radius assessment

**High** per workflow taxonomy because the change:
- Creates accounts that hold long-lived secrets (service-role keys, API keys, SMS gateway auth).
- Sets the data residency posture (one-way for any user data later stored — DPDPA-relevant).
- Establishes the IAM surface for the project (who has admin on each vendor).
- Touches the auth fallback path (MSG91 SMS — sender ID + DLT template approvals in India can take days, so misconfiguration here delays the first user-facing release).

**Who's affected if this goes wrong:**
- *Today, before launch:* only Vivek (the founder); rollback is "delete the empty project."
- *After first user data is stored:* DPDPA-bound — region misconfiguration cannot be silently fixed.

Because no users exist yet, **the right time to execute this is now, before the first feature bet ships and before any real data lands.** Misconfigurations are cheap to fix at this stage; they become expensive within weeks.

## Plan

Each service is provisioned independently; failure of one does not block the others. Execute in any order. Capture every env var into the matching Vercel project setting (production + preview + development scopes) and, for mobile-relevant vars, into EAS Secrets. **No secret value is committed to the repo at any point.**

### 1. Vercel — project + region pin

1.1. `vercel login` (or use existing account).
1.2. From repo root: `vercel link` → create new project `aura-web` (root = `apps/web`).
1.3. In Vercel dashboard → project settings → **Functions** → set default region to `bom1` (Mumbai). Confirm `vercel.ts` `regions: ['bom1']` is respected.
1.4. Settings → **Domains** → leave default `*.vercel.app` for now; custom domain is a later /ops.
1.5. Settings → **Git** → confirm GitHub connection; preview deployments auto-trigger on PRs.
1.6. Settings → **Environment Variables** → create empty placeholders for every key in `.env.example` (values populated in subsequent steps).
1.7. Run `vercel env pull .env.local` from repo root to verify pulling works.

**Captures:** project URL, project ID (recorded in `vercel.ts` if needed).
**Does NOT capture secrets yet** — those come from steps 2–6.

### 2. Supabase — project in `ap-south-1` + extensions + migrations

2.1. Supabase dashboard → new project `aura` in **Mumbai (ap-south-1)**. Choose the smallest production-grade compute tier; right-size later.
2.2. Project Settings → API → copy:
  - `Project URL` → `SUPABASE_URL`
  - `anon (public) key` → `SUPABASE_ANON_KEY`
  - `service_role` key → `SUPABASE_SERVICE_ROLE_KEY` *(never expose to client; Vercel server-only)*
  - Project Settings → Database → `Connection string (URI)` → `DATABASE_URL`
2.3. Database → Extensions → enable: `pg_uuidv7`, `vector`, `citext`, `pgcrypto`.
  - *If `pg_uuidv7` is not yet available in your Supabase region/version, fall back to the community Postgres extension or install via SQL: `CREATE EXTENSION IF NOT EXISTS "pg_uuidv7";` — note in the execution log if a manual install was needed.*
2.4. Install Supabase CLI locally (`brew install supabase/tap/supabase`).
2.5. From repo root: `supabase login`; `supabase link --project-ref <project-ref>`.
2.6. Run migrations: `cd packages/db && supabase db push`. Confirms 0001 through 0006 apply cleanly.
2.7. Verify: SQL editor → `SELECT id, handle FROM users LIMIT 0;` returns empty result without error.
2.8. Settings → API → enable **Restrict service_role key to specific schemas** if available (`public` only).
2.9. Push to Vercel env: `vercel env add SUPABASE_URL`, `vercel env add SUPABASE_ANON_KEY`, `vercel env add SUPABASE_SERVICE_ROLE_KEY`, `vercel env add DATABASE_URL` (each for production + preview + development).

### 3. Vercel AI Gateway — Anthropic + OpenAI providers

3.1. Vercel dashboard → AI → **AI Gateway** → enable for the `aura-web` project.
3.2. Providers → add **Anthropic** → paste Anthropic API key (create at console.anthropic.com if you don't have one).
3.3. Providers → add **OpenAI** → paste OpenAI API key (create at platform.openai.com).
3.4. Settings → **Zero data retention** → enable (Anthropic + OpenAI both support; matches § DPDPA posture).
3.5. Copy AI Gateway API key → push to Vercel env as `AI_GATEWAY_API_KEY` (production + preview + development).
3.6. Provider keys do NOT need to be in Vercel env directly — Gateway holds them server-side. *(Architecture decision: only `AI_GATEWAY_API_KEY` is set; provider keys are configured at the Gateway level. This avoids duplicating secrets and keeps the boundary in `packages/ai/src/gateway.ts` clean.)*
3.7. Verify: from Vercel dashboard → AI Gateway → "Test request" using model string `anthropic/claude-haiku-4-5` returns a response.

### 4. MSG91 — SMS OTP fallback

**Note:** India SMS sender-ID + DLT template approvals can take 2–5 business days. Start this step *first* if the dependency-chain timing matters; the auth fallback path is not blocking for first feature-bet kickoff but IS blocking for first user-facing release.

4.1. msg91.com → sign up for an account; complete KYC (PAN + GST if applicable for India billing).
4.2. Apply for a **DLT registered sender ID** (header) — typical format `AURAID`. Approval is via TRAI's DLT portal; 2–5 business days.
4.3. Create an **OTP template** matching the wording Aura will send (sample: "Your Aura code is {{otp}}. Valid 5 minutes. Never share."). Submit for DLT approval.
4.4. Once approved, capture:
  - **Auth Key** → `MSG91_AUTH_KEY`
  - **Template ID** → `MSG91_TEMPLATE_ID`
  - **Sender ID** → `MSG91_SENDER_ID`
4.5. Push to Vercel env (production + preview + development).
4.6. Verify: from MSG91 dashboard → "Send test OTP" to your phone using the approved template.

### 5. Bhashini — vernacular ASR/TTS for Hindi (+ English eval)

5.1. bhashini.ai → register as a developer; complete onboarding.
5.2. Apply for an **inference API key** (`ULCA Userid` + `ULCA API Key` + `Inference API Key`).
5.3. From Bhashini model directory, identify and bookmark:
  - **ASR — Hindi:** the current production-recommended IndicASR model id.
  - **TTS — Hindi:** the current production-recommended IndicTTS model id (male + female voices).
  - **ASR — English (Indian accent):** identify candidate (Bhashini OR Whisper — pick later in eval).
  - **TTS — English:** same — Bhashini OR native iOS/Android TTS (decide in feature bet).
5.4. Capture model IDs into `.env.example` as constants (a follow-up tiny PR — not part of this ops doc since it IS a code change).
5.5. Push secrets to Vercel env:
  - `BHASHINI_USER_ID`
  - `BHASHINI_API_KEY`
  - `BHASHINI_INFERENCE_API_KEY`
5.6. Optional but recommended: create Sarvam API account (sarvam.ai) for fallback path — `SARVAM_API_KEY` to Vercel env.
5.7. Verify: from Bhashini dashboard or via `curl`, run a single Hindi TTS request — confirm audio output is decodable.

### 6. Sentry — errors + RUM

6.1. sentry.io → create org (if not already done) → create two projects:
  - `aura-web` (Next.js platform)
  - `aura-mobile` (React Native platform)
6.2. Copy DSNs:
  - `aura-web` DSN → `SENTRY_DSN` (Vercel env)
  - `aura-mobile` DSN → also `SENTRY_DSN` for the mobile build, set via `eas secret:create`
6.3. Create an auth token (Sentry → Settings → Auth Tokens) → `SENTRY_AUTH_TOKEN` (used by Sentry build plugins to upload source maps).
6.4. Push to Vercel env (`SENTRY_DSN`, `SENTRY_AUTH_TOKEN`).
6.5. Push to EAS Secrets: `eas secret:create --scope project --name SENTRY_DSN --value <mobile-dsn>` (run from `apps/mobile`).
6.6. Configure Sentry data-scrubbing rules → match the PII fields per § Cross-cutting standards (handle hashes, never raw conversation content).
6.7. Set up Slack integration → route P0/P1 alerts to a `#aura-incidents` channel (or equivalent).

### 7. Final env sync

7.1. From repo root: `vercel env pull .env.local` → confirm every key from `.env.example` resolves.
7.2. Confirm `.env.local` is git-ignored (already in `.gitignore`).
7.3. From `apps/mobile`: `eas env:pull` (if applicable) or document manual sync.
7.4. Commit a tiny follow-up PR ONLY if `.env.example` needs new keys (e.g., Bhashini model IDs from step 5.4) — flagged as a separate /ops if substantial.

### Decisions

- [2026-05-24] [Enterprise/Solution Architect] Provision all 6 foundational services in a single ops change rather than 6 separate /ops invocations.
  - **Rationale (required):** Each service is independently provisioned but together close one architecture P1 Issue. A single doc + one rollback procedure is easier to operate than six small docs that all reference each other. Per-service execution is parallelisable; this doc structures the steps so partial execution is safe.
  - **Area (required, tag):** ops / process.
  - **Alternatives considered (required):** Six separate `OPS-00{1..6}` files (rejected — fragments the runbook for one logical setup task); split only the auth-related ones (MSG91 + Sentry vs. infra ones) (rejected — false boundary; all six block the same P1 Issue).
  - **Reversibility:** easy — could split later if a single service's rollback proves complex enough to warrant its own doc.

- [2026-05-24] [Enterprise/Solution Architect] Anthropic + OpenAI provider keys live in the AI Gateway, not directly in Vercel env vars on the project.
  - **Rationale (required):** AI Gateway is the boundary (per architecture § Stack → AI orchestration). Keeping provider keys at the Gateway level (not duplicated into Vercel project env) honours the single-source-of-truth rule and matches the `packages/ai/src/gateway.ts` boundary. Only `AI_GATEWAY_API_KEY` is in Vercel env.
  - **Area (required, tag):** ops / secrets.
  - **Alternatives considered (required):** Put `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` directly in Vercel env (rejected — bypasses Gateway boundary and tempts direct SDK use).
  - **Reversibility:** medium — adding direct provider keys later is one dashboard action; removing once code references them is harder.

- [2026-05-25] [Engineer / Vivek] **R-OPS-2 materialized — implement `uuidv7()` in plpgsql in migration 0001 (Option C).** Pre-flight `SELECT * FROM pg_available_extensions WHERE name = 'pg_uuidv7'` returned zero rows for the new `ap-south-1` Supabase project. Migration 0001 was edited in commit (see post-this-decision commit) to remove `create extension pg_uuidv7` and define `uuidv7()` as a plpgsql function (48-bit unix-ms timestamp + 74 bits random from `pgcrypto.gen_random_bytes`, version 7 + RFC 4122 variant bits set per spec).
  - **Rationale (required):** Three fallback paths existed. (A) Supabase support ticket = days to weeks of wait + not guaranteed. (B) Switch to UUID v4 via `gen_random_uuid()` = loses time-ordered + sortable property that architecture chose v7 for + requires architecture v2 amendment. (C) Implement v7 in plpgsql = ships now, preserves the property, zero changes to other migrations, marginally slower than the C extension (invisible at our scale — function-call overhead vs C is negligible at <<10K writes/sec). Option C is exactly the "install via SQL" fallback the OPS-001 runbook anticipated in step 2.3. The bit math (`get_byte`/`set_byte` masking byte 6 to `0x7X` for version, byte 8 to `0x{8,9,A,B}X` for variant) is RFC-9562 compliant.
  - **Area (required, tag):** ops / database / migration / fallback.
  - **Alternatives considered (required):** A (support ticket — rejected: blocks execution); B (v4 — rejected: amends architecture for ops-layer constraint, wrong direction).
  - **Reversibility:** easy — if `pg_uuidv7` becomes available later, drop the plpgsql function + add `create extension pg_uuidv7`; existing UUIDs are spec-compliant v7 either way so data carries over without re-write.

- [2026-05-25] [Engineer / Vivek] **Defer MSG91 provisioning to a successor /ops.** Step 4 (MSG91 — DLT sender ID + OTP template + auth key) is skipped in this execution.
  - **Rationale (required):** TestFlight is an invited internal cohort (~50 hand-picked per AUR-1 brief), 100% passkey-capable by selection. The OTP fallback path exists for the ~5–15% device cohort that fails capability detection at public-store launch — not for TestFlight. Spending ops time + DLT approval latency (2–5 business days) provisioning MSG91 right now buys nothing for the TestFlight cohort and risks creating a stale auth-key holding pattern until Story 2 ships.
  - **Area (required, tag):** ops / scope / sequencing.
  - **Alternatives considered (required):** Provision MSG91 now and let the DLT clock run in parallel (rejected — adds operator time + risk of leaked auth key sitting in Vercel env for weeks before first use); ship public-store launch with no fallback (rejected — separate concern; Story 2 must provision MSG91 when it's promoted from stub).
  - **Reversibility:** easy — re-open OPS-001 (or open OPS-002) when Story 2 of AUR-1 is promoted from stub. R-OPS-1 (DLT latency) stays valid; defer its concern until that point.

- [2026-05-24] [Enterprise/Solution Architect] Tag this change `hygiene: true` (standalone) rather than bet-linked.
  - **Rationale (required):** The provisioning isn't driven by a specific feature bet — it's foundational infrastructure that every future bet depends on. Per `compass/config.yaml` (`hygiene_path_enabled: true`), standalone hygiene is the right shape.

### Risks

- [2026-05-24] [Enterprise/Solution Architect] **R-OPS-1: India DLT (MSG91) approval latency.** Sender-ID + template approval by India's TRAI DLT portal can take 2–5 business days; rejected templates restart the clock.
  - **Likelihood (required):** medium (first-time submissions are commonly rejected for wording).
  - **Impact (required):** medium (delays only the OTP fallback path; passkey-primary auth ships without it; affects ~5–15% of users at launch).
  - **Mitigation (required):** Start MSG91 step *first* in execution order so the DLT clock runs in parallel with other provisioning. Use template wording from established Indian fintech examples (banking OTPs) which are pre-approved patterns.
  - **Status update (2026-05-25):** N/A for this execution. MSG91 step deferred (see Decision above); R-OPS-1 stays on the books for the successor /ops that ships with Story 2 of AUR-1.
  - **Area (required, tag):** ops / auth / vendor.

- [2026-05-24] [Enterprise/Solution Architect] **R-OPS-2: Supabase `pg_uuidv7` extension availability uncertainty.** The migrations assume `pg_uuidv7()` is available; Supabase's stock extension list as of 2026-05-24 may or may not include it for `ap-south-1`.
  - **Likelihood (required):** medium.
  - **Impact (required):** high (migrations 0001–0006 will fail to apply if `uuidv7()` is unresolved — blocks the entire dev environment).
  - **Mitigation (required):** Pre-flight check: run `SELECT * FROM pg_available_extensions WHERE name = 'pg_uuidv7';` in Supabase SQL editor before pushing migrations. If unavailable: (a) install via support request, (b) install manually via `CREATE EXTENSION` if Supabase allows non-listed extensions, (c) fall back to community extension or to `pgcrypto`-generated UUID v4 with a Decision-amendment to architecture (creates v2 of architecture.md per workflow rules — not preferred). Note outcome in execution log.
  - **Area (required, tag):** ops / database.

- [2026-05-24] [Enterprise/Solution Architect] **R-OPS-3: Secret leak during provisioning.** Provisioning involves pasting API keys into dashboards and shell history. Misplaced paste → key in chat / screenshot / clipboard manager.
  - **Likelihood (required):** low-medium (depends on operator hygiene).
  - **Impact (required):** high (any leaked key = grant of attacker access; rollback is revoke-and-rotate per R-3 / R-4 / R-5).
  - **Mitigation (required):** (1) execute in a single sitting; (2) never paste secrets into Claude prompts (Claude never sees raw secrets — it sees only the env var *names*); (3) clear clipboard after each paste; (4) confirm `vercel env add` reads from stdin (no shell history); (5) immediately after provisioning, generate one fresh test key per service and revoke the originals to confirm the revoke flow works (also tests rollback step partially).
  - **Area (required, tag):** ops / secrets / security.

- [2026-05-24] [Enterprise/Solution Architect] **R-OPS-4: Region misconfiguration.** Provisioning a service in the wrong region (e.g. Supabase in US East instead of `ap-south-1`) violates the Sustainability + Security fitness functions ("100% India region") and cannot be silently fixed once data lands.
  - **Likelihood (required):** low (region is a clearly-labelled choice in every dashboard).
